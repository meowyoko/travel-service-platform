## 总体架构

```mermaid
flowchart LR
    A["管理端 React"] --> API["Fastify API"]
    E["员工端 React H5"] --> API
    API --> U["业务用例与权限校验"]
    U --> DB["SQLite + Drizzle"]
```

技术选择：

- `apps/api`：Fastify 5，兼容项目当前 Node 22；Fastify 5 要求 Node 20+。[官方说明](https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/)
- 数据库：SQLite + Drizzle ORM。
- 接口校验：JSON Schema/TypeBox，Fastify 原生支持请求与响应校验。[官方说明](https://fastify.dev/docs/v5.8.x/Reference/Validation-and-Serialization/)
- 认证：服务端 Session + HttpOnly Cookie。
- 部署前提：单台 VPS、单个 API 实例。如果一开始就需要多实例，直接改 PostgreSQL。

## 数据表

一期建立这些规范化表：

```text
operator_accounts
operator_page_permissions
groups
employees
quota_accounts
service_products
product_visible_groups
personal_intents
personal_orders
quota_transactions
service_reviews
sessions
```

设计原则：

- 密码只保存哈希，不再进入领域 DTO。
- 商品旅游扩展、图库、订单商品快照可以先用 JSON 字段。
- 额度使用整数存储。
- 手机号、用户名、集团名、商品名、订单号建立唯一约束。
- 一条订单最多一条评价。
- 所有额度扣减、退回和流水写入同一事务。Drizzle 支持事务及保存点。[官方说明](https://orm.drizzle.team/docs/transactions)

## 认证与权限

- 管理端、员工端分别登录。
- Cookie 使用 `HttpOnly + SameSite=Lax + Secure（生产）`。
- Session 保存于数据库，退出或停用账号后可立即失效。
- 密码使用 Node 内置异步 `scrypt`，随机盐不少于 16 字节；避免额外原生加密依赖。[Node 官方文档](https://nodejs.org/download/release/latest-v20.x/docs/api/all.html)
- 员工 ID 从 Session 获取，接口不接受前端冒充的 `employeeId`。
- 操作人从管理端 Session 获取，不接受前端传入任意名字。
- 页面权限必须在 API 再校验一次，不能只依赖前端菜单隐藏。

## 实施顺序

1. 创建 API、数据库迁移和 Mock 种子脚本。
2. 完成双端登录、Session、权限和数据隔离。
3. 接入集团、员工、额度、服务商品。
4. 接入员工商品浏览和意向提交。
5. 接入后台意向转订单、确认扣额度。
6. 接入员工订单与额度变化。
7. 迁移退款、评价、账号管理等现有能力。
8. 删除前端运行时 Mock，保留 Mock 作为开发种子和测试数据。
9. 补数据库事务、API 权限和完整闭环测试。

## 验收标准

- 员工提交意向后，管理端重新加载即可看到。
- 后台确认订单后，员工端额度和订单同步变化。
- API 重启后数据仍存在。
- 两次并发确认不能重复扣减额度。
- 员工无法读取其他员工或其他集团的数据。
- 普通运营账号无法绕过页面权限调用接口。
- 四项现有验证继续通过，并增加数据库/API 集成测试。

SQLite 适合当前单机原型；运行时使用单连接。若开启 WAL，需要先确认 SQLite 已包含官方近期 WAL 修复，因为 WAL 虽提高读写并发，但仍只有一个写入者且要求同机文件系统。[SQLite WAL 官方说明](https://www.sqlite.org/wal.html)

凛确认“单台 VPS、单 API 实例、SQLite 起步”这个前提后，我就按这套方案拆第一轮实施清单，先做 API、数据库和认证。
